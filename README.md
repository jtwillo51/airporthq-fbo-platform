# Ridgeline Aviation / AirportHQ

A two-surface FBO (fixed-base operator) platform — a public site and a staff
operations portal — with an AI analysis layer over 19 months of operating data.

**Ridgeline Aviation, Summit Jet Center and Ridgeline Regional Airport (KXRG) are
fictional.** Any resemblance to a real operator is coincidental.

```
public-site/          Public marketing site      (Next.js 16, TS)  :3000
airporthq-platform/   Staff operations platform  (Next.js 16, TS)  :3001
shared-data/          JSON data layer (stands in for a backend)
scripts/              Data generation
global-resources/     Design tokens and a static interactive demo
```

## Running it locally

### Prerequisites

- **Node.js 20.9 or newer** (Next.js 16 requirement) and npm
- **Git**
- *Optional:* Python 3.10+ if you want to regenerate the demo data
- *Optional:* an Anthropic API key, only for live AI mode (see [AI modes](#ai-modes))

No database, backend, or account is needed. Both apps read JSON straight from
`shared-data/`.

### 1. Clone

```bash
git clone https://github.com/jtwillo51/airporthq-fbo-platform.git
```
```bash
cd airporthq-fbo-platform
```

### 2. Start the staff platform (AirportHQ) on port 3001

```bash
cd airporthq-platform
```
```bash
npm install
```
```bash
npm run dev -- -p 3001
```

Open http://localhost:3001.

### 3. Start the public site on port 3000

In a second terminal, from the repo root:

```bash
cd public-site
```
```bash
npm install
```
```bash
npm run dev
```

Open http://localhost:3000.

The two apps run independently, so you can start just one. Always run each
from inside its own folder: both find the data at `../shared-data`, relative
to where they start.

### 4. Optional configuration

Everything works with no configuration. To change the platform defaults, copy the
example file inside `airporthq-platform/`:

```bash
cp .env.local.example .env.local
```

| Variable | App | Default | Purpose |
|---|---|---|---|
| `AI_MODE` | platform | sample | Set to `live` for real Claude calls |
| `ANTHROPIC_API_KEY` | platform | none | Needed only when `AI_MODE=live` |
| `NEXT_PUBLIC_DEMO_TODAY` | platform | `2026-08-19` | Pinned "today"; `live` uses the real clock |
| `WEATHER_STATION` | public site | `KDEN` | Real station for live METAR/TAF (the demo airport is fictional) |

Set `WEATHER_STATION` in `public-site/.env.local` instead. Restart `npm run dev`
after changing env files. `.env` and `.env.local` are
gitignored.

### Resetting and regenerating data

Edits made in AirportHQ (fuel prices, site content, log entries) are written
back into the JSON files in `shared-data/`. To throw them away:

```bash
git checkout -- shared-data
```

To rebuild the whole dataset from the seeded generator (the output is the same
every run):

```bash
python scripts/generate_timeline.py
```

### Production build and evals

```bash
npm run build
```
```bash
npm start -- -p 3001
```

The AI insights eval (`airporthq-platform/`) calls the live model and needs a
funded `ANTHROPIC_API_KEY`:

```bash
npm run eval:insights
```

## AI modes

**Sample mode is the default** — the AI panels return pre-written responses
with a simulated delay, so the whole app is explorable with no key, no spend,
and no account in good standing. Scripted output is badged **"Sample
response"**; it is never presented as model output. The figures those responses
quote are real arithmetic over the dataset and match the Profitability page
exactly.

To run the same panels against the real API, set both:

```bash
AI_MODE=live
ANTHROPIC_API_KEY=sk-ant-...
```

The key is read only inside `/api/ai/*` route handlers and never reaches the
browser. In sample mode the Ask panel answers its six suggested questions and
says plainly that it cannot answer anything else; live mode accepts free-form
questions.

## The demo clock is pinned

`NEXT_PUBLIC_DEMO_TODAY` defaults to **2026-08-19**. Pinning matters: with a
live clock every passing day adds data and shifts every total, which would
silently invalidate the figures quoted in the sample responses and here in this
README. Set it to another date, or to `live`, to change that.

## The data is fabricated

**Every record the application reads is generated.** No real customer, aircraft
owner, contact, invoice, or price appears anywhere in `shared-data/`, in the app
source, or in the scripted AI responses. Aircraft registrations and owner names
are produced from a seeded RNG, not transcribed from any register or customer
list.

The generator was modelled on how a small FBO actually runs its books, but no
real operator's records are included in this repository.

- **Range:** Aug 2025 – Feb 2027 (19 months), generated by
  `scripts/generate_timeline.py` with a fixed seed, so re-running is
  byte-identical.
- **13 of the 19 months are visible** (Aug 2025 – Aug 2026 at the pinned date);
  the rest are held back.
- **Nothing after today is ever displayed.** The timeline deliberately runs six
  months into the future so forecasts can be scored against held-out ground
  truth. `src/lib/clock.ts` clamps every read path to `<= today`; the current
  month renders partial. The single accessor that returns future data is
  `getHeldOutActuals()`, used only for forecast scoring.
- **Seasonality** is modelled for a high-elevation mountain airport: summer peaks
  near 20,000 gal Jet A/month, deep winter falls to ~8,000.

### Deliberate anomalies

Injected at known months so anomaly detection has genuine signal rather than
noise. These are operational events a working FBO would want flagged — not
fabricated data defects:

| Month | Event | What it looks like |
|---|---|---|
| 2025-11 | Engine overhaul | Parts spend spikes well above run rate, dragging net down |
| 2026-01 | Margin squeeze | Wholesale jumps ~$0.85/gal while posted retail lags — margin falls from ~$2.65/gal to ~$1.46 |
| 2026-03 | Jet A tank loss | Cumulative over/short breaches the leak-check threshold (`gallons × 0.01 + 130`), tripping the check to **YES** |

## Business rules

- **Landing / ramp fees** split 80/20 after 5% state sales tax and a 3.5% card
  processing fee: **the FBO keeps 80%**, the airport authority receives 20%.
  Only the FBO share counts toward net profit.
- **Transient hangar stays** are split with a third-party hangar owner who
  receives 70% of net rent.
- **The maintenance shop is cost-only.** Parts spend is modelled but labour
  billing is not, so the line always reads as a loss. This is a deliberate gap
  in the data model, surfaced in the UI and in the AI system prompt so nothing
  recommends shrinking a shop that simply has no revenue side modelled.

## AI features

All server-side, `claude-opus-5` with adaptive thinking:

| Route | Does |
|---|---|
| `/api/ai/insights` | Anomaly detection, most/least profitable service and truck, watch list (Zod-validated structured output) |
| `/api/ai/forecast` | Demand and price projection, optionally scored against held-out months the model never saw |
| `/api/ai/ask` | Streamed natural-language Q&A over the visible data |

`/profitability` is deterministic math and needs no API key.

## Regenerating data

```bash
python scripts/generate_timeline.py
```

This owns every file in `shared-data/` except `fuel-prices.json`,
`site-content.json`, and `business-directory.json`, which are edited live
through the admin UI and are never overwritten by a script.
